# Задание на реализацию CleanTG Server

Согласованный результат текущего репозитория — архитектурный драфт и контракт. Runtime, клиентская синхронизация и production deployment ещё не реализованы. Использовать инструкции и `AGENTS.md` подготовленного проекта владельца; не подменять их инструкциями этого драфта.

## Контекст для нового проекта

CleanTG — модифицированные клиенты Telegram. Android и iOS имеют локальные дневные лимиты вручную выбранного списка, независимый PIN, таймер и блокировку открытого чата. Нужно добавить опциональный backend с произвольным HTTPS URL, едиными правилами/PIN и общим бюджетом одного Telegram-аккаунта между платформами.

Локальная модель должна продолжать работать без сервера. В server mode выбранные чаты открываются только по короткому lease; при обрыве нет автоматического ухода на local mode. Все мутации ограничений, режима и сервера защищены PIN. Конфигурация не обнуляет использованное время.

Прочитать `README.md`, `docs/architecture.md`, `docs/security.md`, `docs/self-hosting.md`, OpenAPI и сценарии. Их статус — draft. Сначала проверить спорные решения ниже, затем менять контракт одновременно с тестами и документацией.

Направление от пользователя 2026-10-13: WebSocket принят как потенциально рабочая real-time стратегия. Предпочтительный кандидат — REST + WSS; Telegram storage/Mini Apps/Serverless для синхронизации не использовать. Выбор Go + PostgreSQL ещё обсуждается. Формат WS сообщений пока не специфицирован: прочитать `docs/realtime.md`, не считать OpenAPI описанием двусторонних кадров.

## До первой реализации

1. Сделать небольшой OIDC PoC с собственным тестовым bot/client: callback, PKCE, nonce, numeric user ID и сверка активного аккаунта. Никаких пользовательских Telegram sessions на backend.
2. Реализовать чистую модель union lease на управляемых server/client clocks и превратить JSON сценарии в исполняемые тесты. Проверить гонки с настоящим PostgreSQL.
3. Подтвердить продуктовый компромисс: TTL 5 секунд и консервативные хвосты при обрыве вместо большого автономного бюджета. Погрешность накапливается при повторных обрывах.
4. Утвердить доверие оператору v1 и видимость peer IDs. Если нужен E2EE первого выпуска, спроектировать ключи и recovery до реализации persistence/API.
5. Выбрать лицензию будущего кода, поддерживаемые версии Go/PostgreSQL и проверенные OIDC/JOSE/DPoP библиотеки. Подписанные токены не реализовывать собственной криптографией.
6. Сделать WS PoC минимум Android+iOS: авторизация с привязкой к ключу устройства, истечение/отзыв, foreground/background, сетевые обрывы, reconnect/snapshot и application-level renew ack. Затем описать кадры отдельной схемой/AsyncAPI и дополнить сценарии. SSE endpoint старого драфта не является обязательством реализации.

## Порядок разработки

| Этап | Результат и приёмка |
| --- | --- |
| 1. Budget domain | Одна timeline, пересечения устройств, expiry/stop, period boundary, out-of-order, clock rollback |
| 2. Persistence | Транзакции/locks, уникальные identity и idempotency, carry-in high-water, cleanup после accounting |
| 3. Identity/devices | Telegram OIDC, bootstrap/enroll, P-256/DPoP, refresh rotation, revocation |
| 4. PIN | Argon2id/pepper, глобальный backoff, scoped capability, PIN change и recovery без сброса расхода |
| 5. API и real-time | REST OpenAPI, WS контракт после PoC, If-Match/412, outbox/reconnect и snapshot |
| 6. Android adapter | Режим/URL UI, monotonic deadline со сном, lifecycle и live blocking, атомарная миграция local/server |
| 7. Другие клиенты | iOS → Desktop → native macOS с тем же контрактом и сценариями |
| 8. Эксплуатация | HTTPS, secrets, observability, restore/clock guard, upgrade и ограниченный пилот |

Первый backend остаётся одним сервисом и PostgreSQL. Не добавлять Kafka/Redis/федерацию/семейные роли/несколько правил до появления конкретного требования.

## Обязательные сценарии

- Два устройства не получают два дневных бюджета; одновременное чтение считается один раз.
- Повтор start/renew с тем же ключом не продлевает разрешение и не списывает повторно.
- Запоздавший renew не отменяет stop; истёкший ответ не оживляет доступ.
- Нет сети → deadline истёк → текущий чат и медиа закрыты, unselected/settings доступны.
- PIN, OIDC credential, access token и ключ другого устройства не заменяют друг друга.
- Изменение лимита/списка/режима не сбрасывает использованное время; stale editor получает 412.
- Новый timezone и системные часы не создают неожиданные сутки; lease не переходит через midnight.
- Restore старой БД не возвращает расход или отозванный токен назад.
- Повтор migration ID и импорт legacy counter не создают бесплатный бюджет.
- Запросы и логи не содержат Telegram auth keys, сообщения, PIN и токены.

## Готовность к пилоту

Пилот допустим после domain/property tests, SQL concurrency tests, API negative/security tests, review OIDC/DPoP и physical device тестов минимум Android+iOS. Docker image и успешный GET health сами по себе не являются приёмкой. До этого сохранять явно обозначенный draft/experimental статус.

Публичные примеры должны оставаться искусственными. Секреты, адреса личной сети владельца, Telegram IDs из реальных баз и артефакты подписания клиентов не включать в этот репозиторий.
