# WebSocket: направление и статус контракта

2026-10-13 пользователь выбрал WebSocket как потенциально рабочую стратегию синхронизации. Это предпочтительный кандидат для real-time обмена. Работающего транспорта, согласованного формата кадров и подтверждённых результатов native PoC пока нет.

Синхронизацию через «Избранное», CloudStorage Mini Apps или Telegram Serverless не рассматриваем. Сохраняется выбор Local либо собственного сервера по HTTPS URL.

## Предлагаемое разделение

- HTTPS REST: OIDC, устройства, PIN, редактор, миграции и получение полного snapshot.
- WSS: события изменения правил/расхода и отзывов; после проверки протокола — start/renew/stop ограниченного просмотра.
- На телефоне соединение поддерживается в активном приложении. При уходе в фон просмотр локально прекращается, stop отправляется best effort. При возврате требуется свежее состояние и новый действующий lease.
- Таймер рисуется локально по подтверждённому сроку; посекундная рассылка показаний не требуется.

Сначала допускается WS для событий при сохранении REST lease-операций из OpenAPI. Это этап проверки транспорта; возможный последующий перенос команд на WS не меняет правила учёта.

## Что сохраняется независимо от транспорта

Сервер считает объединение интервалов, выполняет изменения атомарно и сохраняет результаты до подтверждения клиенту. Перезапуск сервера или закрытие сокета не обнуляет расход. Локальный deadline, period/revision, idempotency и device session/sequence остаются обязательными.

Ping/Pong проверяет доступность соединения. Действующий lease продлевается только подтверждённой сервером операцией приложения; успешный Pong не означает, что бюджет зарезервирован или человек читает выбранный чат. Истечение разрешения блокирует содержимое даже при формально открытом сокете.

TTL 5 секунд, renew примерно каждые 2 секунды и поведение без сети пока остаются продуктовыми предложениями, а не решениями, автоматически принятыми вместе с WS.

## Что должен проверить прототип

1. Привязку WS к авторизованному устройству и его ключу, истечение/обновление авторизации и отзыв. Токены/PIN не помещаются в URL или логи. HTTP DPoP не переносится на кадры без отдельного протокола.
2. Android/iOS lifecycle, сон, Wi-Fi ↔ мобильная сеть, тихий обрыв, reconnect с backoff и получение snapshot после пропуска событий.
3. Упорядочивание команд и ответов: поздний renew не отменяет stop, повтор не продлевает срок, старый snapshot не возвращает предыдущие правила.
4. Ограничения размера сообщений и очередей, медленного получателя, idle timeouts proxy и graceful shutdown. Фоновые сокеты не нужны для корректности.
5. Задержку до подтверждения lease, SQL locks, число DB операций, память/CPU на активное соединение и поведение после аварийного restart. Производительность конкретного стека пока не измерена.

После PoC описать версионированные сообщения отдельной JSON Schema/AsyncAPI и добавить исполняемые сценарии. OpenAPI сейчас описывает REST-семантику и помеченный deprecated предыдущий SSE вариант `/v1/events`; он не описывает готовый двусторонний WS протокол.

## Стек пока является рекомендацией

Кандидат: Go (`net/http` + проверенная WS библиотека), PostgreSQL, `pgx` и `sqlc`; один API процесс и TLS proxy. Версии и библиотеки фиксируются в проекте реализации. Утверждения о преимуществе над Rust/Node.js и вместимости VPS требуют измерений на нашем workload.

SQLite может упростить отдельный личный deployment, но это другой вариант persistence: SQL, часы, конкурентные записи и восстановление необходимо проектировать и проверять отдельно. Текущий контракт транзакций ориентирован на PostgreSQL.
