# Защита серверного режима CleanTG

## Модель доверия

Защищаем изоляцию аккаунтов, конфиденциальность транспорта, управление устройствами и PIN, повторную обработку запросов и целостность общего бюджета. Противники — посторонний клиент, перехватчик сети, обладатель утёкшего токена и пользователь без restriction PIN, использующий штатный клиент.

ОС, приложение и выбранный оператор сервера считаются доверенными. Человек с изменённым клиентом/root/jailbreak, украденным ключом устройства либо административным доступом к серверу может обойти этот уровень защиты. Сервер не может проверить, какие пиксели реально видел пользователь; поэтому «криптографическое доказательство чтения» не входит в обещания.

V1 не использует E2EE. Оператор видит идентификатор аккаунта, выбранные peer IDs, правила и интервалы активности. Он также обрабатывает введённый серверный restriction PIN через TLS. Телефоны, сообщения, имена чатов, Telegram session/auth keys, код входа и 2FA пароль не собираются. Собственный сервер уменьшает круг операторов, которым пользователь доверяет, но не убирает необходимость защищать его.

## Вход и привязка устройств

Идентичность подтверждается Telegram OIDC Authorization Code flow. `api_id`, `api_hash`, присланный `telegramUserId` и наличие строки `user:123` не доказывают владение аккаунтом.

Backend использует фиксированный Telegram issuer/discovery, проверенную библиотеку OIDC, PKCE S256, случайные state и nonce, разрешённый callback и проверку подписи/audience/expiry/nonce ID token. `openid profile` нужны для подтверждённого numeric `id`; OIDC `sub` имеет другое назначение. Phone/bot messaging scopes не запрашиваются. JWKS берётся только у ожидаемого issuer; `jku`/`x5u` и другие внешние URLs из непроверенного JWT игнорируются. См. [Telegram Login](https://core.telegram.org/bots/telegram-login).

Попытка входа одноразовая, живёт не более пяти минут и связана с ожидаемым текущим Telegram ID, ключом устройства и отдельным 256-битным claim secret. Public JWK из тела auth/start обязан совпасть с ключом DPoP proof. Claim secret не включается в browser URL. PKCE Telegram создаётся и хранится backend для своего confidential OIDC client; это не заменяет секрет получения результата и привязку native device. В callback не выдаются токены CleanTG: клиент получает их отдельным запросом с claim secret и DPoP. После ошибки/отмены/таймаута попытка больше не применяется.

OIDC-подтверждение существующего профиля выдаёт только короткую enrollment credential. Для добавления устройства нужен текущий PIN. Создание первого профиля, PIN и первого устройства проводится одной транзакцией с уникальностью identity: две параллельные регистрации не создают два бюджета.

## Ключи и токены

Каждое устройство создаёт P-256 ключ; предпочтительно неэкспортируемый и аппаратно защищённый, если это поддерживает ОС. Private key хранится средствами ОС, а не в preferences/JSON. Backup/клонирование приложения не должно переносить рабочую авторизацию на другое устройство.

Предлагаются access token сроком пять минут и вращающийся refresh token сроком 30 суток. Это параметры драфта, а не требование существующих клиентов. Refresh имеет минимум 256 бит энтропии, на сервере хранится его hash. Повторное использование уже заменённого refresh отзывает token family. Device revocation проверяется сервером на каждом защищённом запросе, поэтому срок JWT не задаёт задержку отзыва.

Токены привязаны к thumbprint ключа устройства по [DPoP RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html). Проверяются `typ`, разрешённый `alg`, подпись, `htm`, `htu`, `iat`, уникальный `jti`, `ath` для resource access и server nonce. Replay cache и nonce должны работать и после перезапуска в пределах допустимого окна. DPoP не шифрует запрос, не покрывает произвольное тело и не заменяет проверку прав; содержимое защищает TLS. Использовать библиотеку JOSE/DPoP, не собственный формат подписей.

`Authorization: DPoP <access token>` и отдельный `DPoP` header обязательны. Enrollment credential использует тот же тип привязки с ограниченным audience/scope. Edit capability и mode-change authorization дополнительно связаны с profile, device, PIN version, сроком и конкретным действием. Передать чужой UUID профиля в URL недостаточно для доступа: данные выводятся из проверенной авторизации.

## PIN и восстановление

Restriction PIN остаётся отдельным PIN из 4–12 цифр. Короткий PIN не является паролем аккаунта, токеном устройства или ключом E2EE. Его перебор особенно опасен при компрометации всего сервера.

Verifier: Argon2id со случайной солью не менее 16 байт и версией параметров. Начальная цель замера — 64 MiB, t=3, p=1; ниже рекомендуемого OWASP минимума 19 MiB/t=2/p=1 не опускаться. Pepper хранится отдельным deployment secret вне БД и её backup; точный метод peppering фиксируется перед реализацией. См. [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

Проверка PIN ограничена по профилю, устройству и IP. Ограничение профиля сохраняется в PostgreSQL и не обходится сменой устройства, параллельным запросом или restart. После трёх ошибок — минимум 30 секунд задержки с ростом до часа. Общий bounded KDF worker pool и ограничения body/concurrency защищают сервис от исчерпания памяти. Отказ по rate limit происходит до дорогого KDF. Неверный PIN и отсутствие профиля не раскрывают данные постороннему пользователю.

PIN открывает edit session максимум на пять минут. Клиент уничтожает локальную capability при Done, уходе редактора, фоне, app lock и смене аккаунта, а сервер получает best-effort revoke. Потерянный revoke не увеличивает TTL capability. Сам сервер не может проверить lifecycle чужого процесса; это обязанность честного клиента. Смена PIN увеличивает PIN version и отзывает все edit/mode capabilities; расход остаётся прежним.

Первый bootstrap предлагает одноразово показать recovery code с 256 битами случайности. На сервере хранится его hash. Восстановление требует свежего OIDC-подтверждения того же аккаунта и recovery code; один OIDC-вход не сбрасывает PIN. Reset PIN сохраняет правила и расход, меняет recovery code и отзывает устройства/сессии. Recovery response нужно сохранить пользователю до завершения: повтор запроса использует тот же безопасный краткоживущий результат, а не создаёт новый профиль. Пока текущий PIN известен, отдельная защищённая операция позволяет заменить утраченный recovery code; старый код после этого недействителен.

Recovery code не сохраняется рядом с обычными клиентскими токенами как автоматический обход PIN. Потеря кода и всех подходящих способов проверки PIN не даёт скрытого API reset. При недоступном сервере онлайн-восстановление не работает; offline detach требует отдельного будущего протокола.

## URL и self hosting

Release-клиенты принимают только HTTPS base URL без userinfo, query и fragment. URL может иметь path prefix, например `https://sync.example/cleantg`. Нормализация не меняет origin или смысл prefix. TLS проверяется системным trust store; для частной CA администратор добавляет её доверие средствами ОС. Переключателя «не проверять сертификат» в release нет.

Access, refresh, edit capabilities и PIN не пересылаются при redirect на другой origin. Лучше вообще не следовать redirect для аутентифицированного API. Все endpoint URLs строятся относительно проверенного base URL; `/v1/meta` не может подменить их произвольными внешними адресами.

OAuth открывается в системном браузере по заранее настроенному серверному маршруту. Приложение никогда не показывает форму «введите пароль Telegram» от выбранного sync-сервера. Backend не исполняет callback URLs от клиента и не ходит по произвольным URL; `PUBLIC_BASE_URL` и OIDC callback задаются оператором, а не `Host`/`X-Forwarded-*` из недоверенного запроса.

Привязки и токены разных instances полностью раздельны. Изменение URL или возврат на Local требует PIN прежнего профиля и отдельной mode-change authorization. Ошибка сети, TLS, OIDC или обнаружение другой instance identity не создаёт пустой локальный профиль.

## Контроль записи и повторов

- Policy update требует сильный `If-Match`, edit scope и новую idempotency key. Stale revision даёт 412, а не overwrite.
- Для каждого mutation хранится `(profile, device, endpoint, idempotencyKey, bodyHash, result)`. Повтор того же запроса возвращает тот же результат; другое тело с тем же ключом даёт 409.
- Idempotency lookup выполняется после проверки device authorization, но до повторного выполнения защищённого побочного эффекта. Успешный retry PIN-change/refresh не должен повторно менять секреты. Для секретных результатов используется короткий зашифрованный response cache, а не plaintext token в общей таблице/логах.
- Идемпотентность start/renew не продлевает `expiresAt` при повторе. Новое продление — новая operation ID и monotonic device sequence.
- Client sequence и server-issued runtime session/fence не позволяют запоздавшему renew заменить более новый stop. Lease из прошлого процесса/периода не переиспользуется; случайный boot UUID клиента сам по себе не задаёт доверенный порядок.
- Usage вычисляется только сервером. Поддельные client duration, клиентская дата или «минус использованное время» не принимаются.

## Данные, журналы и эксплуатация

SQL-запросы параметризованы. Все строки данных имеют profile scope; multi-tenant доступ проверяется на каждом endpoint, включая events, статистику, устройства и idempotency results. Connection pooling и транзакции не должны переносить tenant context между запросами. Role БД у runtime не имеет прав superuser/DDL; migrations используют отдельную роль.

В логах запрещены Telegram/DPoP/access/refresh/enrollment/edit tokens, PIN, recovery codes, OAuth code/state/nonce/claim secret, сырые request body, peer IDs и названия чатов. Диагностика использует request ID, тип операции, агрегированные latency/error codes. OIDC callback query нужно маскировать также в reverse proxy access log. Операторы не должны получать recovery code через трассировку ошибок.

Диски и backup шифруются; ключи хранятся отдельно. Предложение retention: сырые завершённые lease-интервалы семь суток, суточные агрегаты 90 суток, audit без лишнего содержимого 30 суток. Очистка идемпотентна и не удаляет необходимое для незавершённого учёта или retry. Финальные сроки — настройка оператора с понятным описанием пользователю.

Restore старой БД может вернуть расход и отозванные токены назад. Перед восстановлением сервис останавливает выдачу, сохраняет/увеличивает issuance epoch вне восстанавливаемого snapshot, инвалидирует старые токены и разрешения и консервативно закрывает текущий бюджет. После явной проверки оператором и повторной авторизации работа возобновляется. Без такого runbook восстановление backup нельзя объявлять безопасным.

## Условия перед production

Обязательны review OIDC/DPoP/PIN flows, модель concurrent lease на управляемых часах, тесты SQL гонок, replay и out-of-order, восстановление backup, проверка таймера после сна и разрыва сети на каждой платформе. Парсинг OpenAPI и наличие схем не являются security audit. Реальный сервер не считается готовым по одному health check или успешной сборке.
