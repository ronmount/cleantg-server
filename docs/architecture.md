# Архитектура синхронизации CleanTG

## Область и обязательные свойства

Один Telegram-аккаунт получает один серверный профиль с общим списком чатов, дневным лимитом, timezone и отдельным PIN. Устройства этого аккаунта видят один расход. Просмотр настроек и статистики не требует PIN; любая мутация ограничений требует действующей серверной edit session.

Уже потраченное время сохраняется при изменении лимита, списка, PIN и версии правил. Счётчик клиента не заменяет серверный. Сервер не принимает команду «установить usedMs» от обычного устройства. Темы используют ID родительского чата, а несколько окон одного устройства передают объединённое состояние активности.

Текущий локальный MVP остаётся самостоятельным режимом. Сетевая реализация не должна менять его поведение до явного подключения сервера.

## Компоненты

| Компонент | Ответственность |
| --- | --- |
| Нативный адаптер | Видимость чата/медиа, фон, app lock, таймер и мгновенное закрытие содержимого |
| Account coordinator | Выбор режима, привязка текущего Telegram-аккаунта, локальный кэш и миграция |
| Sync transport | HTTPS, DPoP, refresh, revision, SSE, повторы и idempotency |
| API service | Авторизация, PIN, сериализация мутаций, выдача lease |
| Budget service | Серверные периоды и объединение интервалов разрешённого просмотра |
| PostgreSQL | Единственный источник правды для авторизации и бюджета |

Предложение по стеку — Go и PostgreSQL, один процесс API и reverse proxy с TLS. Точные версии и библиотеки фиксируются в проекте реализации после выбора поддерживаемых релизов и проверки зависимостей. Первый запуск поддерживает один writable PostgreSQL и один экземпляр API; горизонтальное масштабирование не является обещанием v1.

Нативный Gate получает решение от одного выбранного provider: local store либо remote coordinator. В server mode локальный `used` не становится вторым источником бюджета; сохраняются только серверный snapshot, mode/migration markers и текущий непереносимый между процессами deadline. Существующий локальный счётчик не должен параллельно списывать время и затем незаметно подмешиваться в server snapshot.

## Идентификаторы и данные

Все account/peer IDs Telegram передаются десятичными строками без преобразования через IEEE-754 `double`. Peer key имеет вид `user:123`, `group:456`, `channel:789`. Secret chats не синхронизируются.

Server instance имеет постоянный случайный `instanceId`; URL сам по себе не является идентичностью сервера. Клиент хранит привязку `(normalizedBaseUrl, instanceId, telegramUserId, profileId, deviceId)`. Неожиданная смена instance ID считается новым сервером и требует защищённого подключения.

| Сущность | Основные поля |
| --- | --- |
| identity | provider issuer, подтверждённый Telegram numeric ID, OIDC subject |
| profile | UUID, identity FK, schemaVersion, policyRevision, PIN version, timezone |
| policy | ruleId UUID, limitMs, selectedPeerKeys, timezone |
| period | UUID, startsAt, endsAt, timezone snapshot, usedMs, lastAccountedAt |
| device | UUID, profile FK, P-256 JWK thumbprint, имя/платформа, статус отзыва |
| device session | Выданный сервером runtime session ID и fence version для текущего процесса |
| lease | UUID, device FK, period FK, policyRevision, issuedAt, expiresAt, closedAt |
| edit session | hash токена, profile/device/action scope, PIN version, expiresAt |
| refresh family | hash refresh token, device FK, expiration, rotation/reuse state |
| carry in | source epoch, period, imported high-water mark, migration ID |
| outbox event | profile revision/event sequence и тип события |

Названия чатов, содержимое сообщений, телефоны, аватары и Telegram auth keys не сохраняются. Сервису достаточно peer key; имя клиент получает из собственной Telegram-базы. Журнал lease не содержит peer ID: серверу нужен факт активного ограниченного просмотра, а выбор конкретного чата выполняет клиент.

## Подключение аккаунта

1. Пользователь выбирает серверный режим и вводит HTTPS base URL. Клиент загружает `/v1/meta`, проверяет совместимость протокола и показывает адрес оператора.
2. Устройство создаёт собственный P-256 ключ в защищённом хранилище ОС. Секретный ключ не передаётся серверу.
3. `/v1/auth/telegram/start` создаёт одноразовую попытку, связанную с thumbprint ключа, случайным секретом получения результата и ожидаемым Telegram user ID. Сервер открывает Telegram OIDC Authorization Code flow через системный браузер.
4. Сервер проверяет OAuth state, PKCE, nonce, подпись ID token, issuer, audience, срок и подтверждённый numeric `id`. Запрашиваются только `openid profile`; дополнительные данные профиля отбрасываются. `sub` нельзя считать Telegram numeric user ID.
5. Клиент получает результат только с исходным секретом попытки и доказательством владения тем же ключом. Подтверждённый ID должен совпасть с аккаунтом, для которого открыт раздел настроек.
6. Если профиля нет, bootstrap атомарно создаёт правила, PIN и первое устройство. Если профиль есть, подключение нового устройства требует его текущего PIN. OIDC-вход сам по себе не сбрасывает PIN и не разрешает изменение правил.
7. Выдаются собственные токены CleanTG, связанные с ключом устройства. Telegram access/id tokens после завершения входа не используются как токены нашего API и не попадают в клиентский кэш/логи.

Telegram Login требует настройки собственного bot/OIDC client для каждого self-hosted instance. Client Secret хранится только на backend. Существующая Telegram-сессия клиента, код входа и пароль 2FA на backend не передаются. См. [официальный Telegram OIDC](https://core.telegram.org/bots/telegram-login).

## Общий бюджет через короткие lease

### Что именно считается

Сервер считает **объединение интервалов разрешённого активного просмотра**, а не сумму клиентских счётчиков. Разрешение выдаётся только для немедленного использования; предзаказ будущих минут запрещён. Бюджет серверного режима может быть немного консервативнее фактического чтения из-за доставки start/stop и потери связи.

Предлагаемые параметры: максимальный TTL 5000 мс, renew примерно через 2000 мс. Они не являются уже согласованной точностью продукта. Нормальное завершение сокращает хвост на момент получения stop сервером; потерянный stop оставляет хвост до expiry. Погрешность одного аварийного окончания ограничена TTL, но несколько обрывов за день могут накопить несколько таких хвостов. Обещать ошибку «не более пяти секунд за сутки» нельзя.

### Серверная транзакция

Любая выдача, продление, закрытие, миграция и изменение политики берёт блокировку строки профиля/периода. Внутри одной транзакции:

1. После получения row lock прочитать доверенное серверное время `now`; в PostgreSQL это свежий `clock_timestamp()`, а не время начала транзакции, полученное до ожидания lock. При обнаруженной аномалии часов выдачу остановить.
2. Закрыть истёкшие периоды и зафиксировать объединение lease-интервалов в старом периоде до его конца.
3. Досчитать `usedMs += measure(union(leases) intersect [lastAccountedAt, now))`. Closed lease заканчивается на `min(expiresAt, closedAt)`. Не удалять истёкшие строки до этого расчёта.
4. Сдвинуть `lastAccountedAt` вперёд. Применить запрошенную операцию, проверив device, PIN scope, revision, period и idempotency.
5. Новый expiry не дальше `min(now + TTL, period.endsAt, now + max(0, limitMs - usedMs))`. Выдать или продлить только lease текущего устройства. Старый expiry и новый ответ не складываются.
6. Записать результат операции и outbox event в той же транзакции. Вернуть snapshot и разрешение после commit.

В любой момент все открытые lease начинаются не позже `now`. Поэтому будущая зарезервированная часть их объединения равна `[now, max(activeExpiry))`, а не сумме TTL устройств. `heldMs` — длина этого будущего объединения; `availableToGrantMs = max(0, limitMs - usedMs - heldMs)`. Эти поля диагностируют резерв. Второе устройство может присоединиться к уже зарезервированному интервалу даже при `availableToGrantMs == 0`.

`remainingMs = max(0, limitMs - usedMs)` — общий ещё не истёкший бюджет, включающий зарезервированное будущее. Клиент не вычитает `heldMs` из показаний таймера второй раз.

### Пример параллельных устройств

При лимите 15 секунд устройство A получает `[0,5)`, B подключается в секунду 2 и получает `[2,7)`. Объединение `[0,7)` расходует 7 секунд, а не 10. Если A закрывает чат в секунду 3, B продолжает `[3,7)` и расход идёт один раз. Если B теряет сеть, после 7 секунды новый просмотр запрещён до нового подтверждения сервера.

На последней секунде оба устройства получают только остаток общего временного горизонта. Сервер не выдаёт по отдельной последней секунде каждому.

### Правила клиента

- Вход в выбранный чат требует действующего lease либо успешного start. До ответа содержимое закрыто. Неограниченные чаты работают без lease.
- Локальный deadline вычисляется как `continuousMonotonicAtRequestStart + validForMs`. Время ожидания ответа уже входит в срок. Нельзя начинать новый полный TTL с момента получения ответа.
- Ответ, пришедший после deadline, с другим period/revision/device/instance, либо от более старого запроса, не открывает чат. Просроченный ответ не оживляет истёкшее разрешение.
- Часы должны продолжать ход во время сна. После перезапуска процесса, смены аккаунта, восстановления backup или устройства старый lease не переиспользуется.
- Перед первым start процесс получает server-issued device session/fence. Произвольный клиентский boot UUID не является доказательством порядка перезапусков; renew из retired session отвергается независимо от его sequence.
- Перед stop/уходом в фон/блокировкой приложение локально отзывает доступ; сетевой stop отправляется best effort. При возобновлении нужен новый lease.
- Приложение блокирует открытые выбранные чаты и связанное медиа при deadline, даже если последующий HTTP-запрос ещё ожидает ответа.
- Пользовательские часы и дата не влияют на серверный срок. Несколько окон устройства объединяются до отправки активности.

При неизменной политике это ограничивает разрешённый доступ общим бюджетом. Уменьшение лимита или отзыв устройства не могут мгновенно отозвать уже выданный permit у недоступного по сети честного клиента: максимальная задержка — его остаточный TTL. Онлайн-клиент применяет событие сразу. Эта граница должна быть видна в требованиях.

## Периоды и часы

Сервер использует фиксированный IANA timezone профиля, например `Asia/Irkutsk`. Он выдаёт `periodId`, UTC starts/ends и timezone. Длина календарных суток при DST может составлять 23 или 25 часов; число минут бюджета от этого не меняется.

Lease не пересекает полночь. Для нового периода требуется новый запрос; полученный до полуночи ответ не даёт бюджет следующих суток. Уже закрытый period не открывается повторно после rollback часов.

Изменение timezone требует PIN, сохраняет текущий period и расход, вступает в действие после его окончания. Следующая граница определяется новым timezone. Частичный переходный день нужно явно показывать, а не создавать скрытый сброс сейчас. Смена timezone ОС устройства не меняет серверную политику.

В v1 требуется мониторинг скачков времени и fail closed при rollback/недостоверном времени. Одного `max(now, previousNow)` недостаточно: при замороженных часах повторы renew могут создавать бесконечное чтение. После restore БД сервер не начинает выдавать lease, пока не подтверждены часы и эпоха восстановления.

## Изменение правил и события

`GET /v1/profile` возвращает политику, snapshot бюджета и сильный ETag вида `"policy-7"`. `PUT /v1/profile/policy` требует `If-Match`, action-scoped edit session и Idempotency-Key. Сначала досчитывается расход, затем меняются правила и revision. Конфликт редакторов возвращает 412 с текущим snapshot; автоматического last-write-wins нет.

Удаление peer сразу освобождает его на устройстве редактора. Онлайн-устройства получают обновление через SSE. Клиент без сети продолжает только до собственного TTL и затем запрашивает свежую политику. Старые lease после изменения revision не продлеваются; уже закрытый peer нельзя открыть по старому ответу.

SSE `/v1/events` — уведомление об изменениях, а не источник правды. После reconnect или разрыва event sequence клиент делает GET snapshot. SSE использует авторизацию в header, не токен в query string. Потеря событий не отключает проверку lease и revision.

Ответы HTTP тоже могут переставляться. Coordinator не применяет snapshot с более старой event sequence/policy revision или уже закрытым period; при неоднозначности получает свежий GET. Старый успешный idempotent retry не уменьшает показанный расход и не возвращает предыдущий выбранный список. Это проверка версии snapshot, а не объединение счётчиков разных устройств через `max`.

## Миграция режимов

Режим и URL выбираются на каждом устройстве для каждого аккаунта. Отключение одного устройства не отключает остальные. После осознанного перехода в локальный режим независимость бюджетов явно показывается пользователю.

| Переход | Поведение |
| --- | --- |
| Локально → новый пустой серверный профиль | Проверить локальный PIN, подтвердить аккаунт, создать серверный PIN, импортировать правила и текущий расход как одноразовый carry-in |
| Локально → существующий профиль | Подтвердить аккаунт и серверный PIN; по умолчанию принять серверные правила; импорт локальных правил является отдельной явной мутацией |
| Сервер → локально | Онлайн проверить серверный PIN, закрыть lease, получить snapshot и mode-change authorization; атомарно сохранить правила и carry-in расход, создать новый локальный verifier из введённого PIN |
| Изменить URL | Защищённое отключение старого instance и независимое подключение нового; никакие токены/PIN не пересылаются между origins |

Исторические локальные MVP имеют только счётчик, поэтому точное объединение их расхода с чужими серверными интервалами невозможно. Для импорта нужен явный консервативный carry-in, а не `max(counterA,counterB)` или замена серверного used. Повтор одного migration ID ничего не добавляет; для source epoch хранится high-water mark, следующая отправка добавляет только ещё не импортированную дельту. При известной исходной серверной базе переносится только локальная дельта после неё. Неопределённое пересечение может завысить расход; это показывается до подтверждения PIN.

Первый импорт/выход не создаёт новый дневной период. Snapshot фиксирует границу текущих суток, которую локальный адаптер обязан сохранить до её окончания. Переход требует атомарной записи режима, кэша, verifier и migration marker: сбой не должен оставлять пустой локальный профиль.

Mode-change grant краткоживущий и привязан к устройству. Доступ локально прекращается ещё до его запроса. Срок проверяется continuous monotonic deadline от начала запроса; после атомарного сохранения клиент очищает прежние credentials и best effort отзывает старое устройство. Сетевой сбой на cleanup оставляет серверную запись до истечения/отзыва, но не возвращает локально удалённый private key. Grant не удаляет профиль и не отключает другие устройства.

Grant также выдаёт `sourceEpochId`; сервер сохраняет для него неизменяемую исходную базу расхода и period. При возврате устройства delta вычисляется относительно этой серверной записи. Клиент не может прислать произвольное число «это уже учтённая база». У неизвестного новому instance source epoch такая база отсутствует, поэтому перенос остаётся явным консервативным импортом.

При недоступном сервере v1 не позволяет переключение на локальные правила/другой URL по локальному cached PIN. Кэш предназначен для чтения. Recovery при потере сервера — отдельный последующий дизайн; встроенного аварийного сброса расхода нет.

## Этапы развития

В v1 нет большого офлайн-бюджета, федерации серверов, E2EE, семейных ролей, отдельного веб-редактора и нескольких списков. Позже можно выдавать автономные невозвращаемые бюджетные ваучеры с серверным резервом; это отдельная политика, а не локальный fallback. Варианты E2EE должны учитывать случайные ключи данных, перенос между устройствами и восстановление: короткий PIN не годится как единственный ключ шифрования.
